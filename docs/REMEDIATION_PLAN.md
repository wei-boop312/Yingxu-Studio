# SOP 闭环问题解决方案

更新日期：2026-11-18。依据：[审计清单](audit/FINDINGS.md)、[SOP 原文](sop/README.md)和当前两个子工程。

**状态：方案已记录，代码尚未修复，15 项审计问题均保持待处理。本文件描述目标行为与验收要求，不代表现有功能。**

实施顺序：先修执行可靠性，再补 SOP 数据模型与最小交付闭环，最后接通 ComfyUI 并完成真实环境验收。保留现有资产、任务、报价快照、租约与回执基础。

## 1. 单张任务升级为商品套图项目

对应 G-01、G-02、G-04、G-08、G-09。

### 需要补充的业务对象

| 对象 | 必须记录的内容 |
| --- | --- |
| 商品与 SKU | 型号、变体、所属商品、配件清单、适用事实与素材范围 |
| 制作项目 | 目标 SKU、任务类型、市场、语言、用途、套图范围和导出规格 |
| 商品事实 | 已确认/未知/冲突状态、来源、适用 SKU、条件、版本、确认记录 |
| 参考素材 | 不可变素材版本、哈希、职责、可见面、已确认角度与关联事实 |
| 图号/槽位 | 稳定 ID、显示编号、目标、所需证据、文案、允许角度、制作路线和缺项原因 |
| 制作版本 | 输入事实/素材/计划/工作流快照、执行意图、输出版本与回执 |
| 验收与交付 | 被审核文件版本、判定依据、问题、交付范围及清单 |

关系为：商品 → SKU → 制作项目 → 图号 → 制作版本 → 验收记录 → 交付文件。一个图号可以有多个历史制作版本；审核必须明确针对哪一个版本。

最小版本先采用一个项目绑定一个 SKU。沿用现有用户/租户隔离，不允许越权引用素材或其他 SKU 的事实。同一事实可声明适用多个 SKU，但必须有明确依据，不能因名称相似而自动共用。

保留已有原图理解与人工校订流程，补充结构、接口、配件、允许视角和未知项的证据引用。未拍摄的面保持未知，不自动认定无结构或允许生成。

事实修订生成新版本，并列出受影响的文案、计划及图号。历史任务快照保持不变，无关图不应被一并作废。市场、语言和图片用途通过界面明确选择，不再机械固定为 MAIN、US 或 RU；未核实的平台规则保留复核状态。

### 验收要求

- 同型号两个 SKU 的尺寸、配件、文案与输出不会串用。
- 每个已确认事实和锁定项都能回到对应素材或文档证据。
- 未知底面不能直接进入允许生成的视角，冲突参数不能自动进入发布文案。
- 修改接口或尺寸后，可以列出应复核的具体图号，并保留历史任务依据。

## 2. 固定六模块改为可变套图编排

对应 G-03，并依赖第 1 节的数据模型。

现有六模块详情页保留为一种模板。通用套图编排由业务层管理，支持按项目指定图数、图号、比例、尺寸与制作路线。不能仅把代码里的 6 替换成 10。

重点调整位置：架构师的 `workflow_architect/detail_page.py`、`web/js/detail_runner.js`、`web/js/detail_panel.js`，以及业务侧新增的项目/图号接口。入口校验、执行进度、预览和导出都要使用明确的槽位 ID，不依赖固定数组长度推断业务身份。

资料就绪、执行、验收和交付分别记录。缺项应保存缺少的事实/素材及受影响原因，避免一个槽位待资料导致整个项目无法继续。

| 示例 | 条件 | 预期行为 |
| --- | --- | --- |
| 01—08 | 各自所需证据齐全 | 可继续制作、审核和独立交付 |
| 09 尺寸图 | 缺已确认尺寸 | 保留编号，待补尺寸，不编造参数 |
| 10 包装配件图 | 缺当前 SKU 清单或对应视觉参考 | 保留编号，待补资料，不凭清单想象配件外观 |

允许对已通过验收的 8 张作部分交付，清单标明“已交付 8/10，09、10 待资料”。这是部分交付，不能将整套项目标为完成。补资料后只推进受影响槽位。

### 验收要求

- 可变图数正常编排，原有六模块模板仍可使用。
- 09/10 待资料时，其他已满足条件的图片可以完成审核与部分交付。
- 槽位编号、进度、输出版本和清单对应一致，不静默补图或漏报缺项。

## 3. 修复工作流校验漏洞

对应 D-01、D-02、D-03。

主要调整架构师 `workflow_architect/validator.py`、`registry.py`、`schemas.py`，并核对编译与服务入口。

- 端口索引必须为合法整数，拒绝 bool、负数和超过输出数量的索引；异常输入返回结构化错误。
- 检测自环、多节点环及无效输出连接，对正常共享上游的无环图保持支持。
- 保留真实节点参数定义，检查字段、必填项、标量类型、枚举与数值边界。按节点实际合同处理动态字段，不简单假定所有节点输入都一样。
- 规划、导入、编辑、编译与执行前使用一致的校验规则；保留草稿与可执行工作流的区别。
- 以目标 ComfyUI 的实际节点能力核对本地判断。无法确认时返回待核实或明确错误，不直接标为可执行。

### 验收要求

审计中的越界端口、极端负索引、循环依赖、未知输入及非法数值均被正确拒绝；正常工作流仍通过。各公开入口返回一致结果，无未处理异常。最后与真实宿主环境对照，单元测试不能替代宿主验收。

## 4. 任务领取与去重移到服务端

对应 D-04、G-06，并与 G-10 的资源快照共同实施。

浏览器进度只负责展示与操作恢复。复用电商平台现有持久化、幂等、租约、fencing token 与调用回执设计，将 ComfyUI 提交接入同一个受控服务。

目标流程：先持久化执行意图 → 原子领取任务 → 保存提交中状态 → 调用执行端 → 保存执行编号与原始回执 → 查询状态 → 回收并核对输出。

关键约束：

1. 每次用户确认的制作有稳定执行意图 ID；数据库唯一约束包括用户/租户范围。重复点击、页面刷新和重连沿用原意图，不生成新意图掩盖重复请求。
2. 同一意图同一时刻只允许一个有效执行者，过期执行者不能覆盖新进度。租约只协调任务所有权，不能证明外部执行端从未收到请求。
3. 提交响应丢失时进入“状态待核实”，先查询和对账，禁止因超时或租约过期直接重投。无法证明未提交时保持未知并提供人工处理入口。
4. 保存业务任务 ID、执行意图 ID、ComfyUI 执行编号、输入快照与输出哈希的对应关系。
5. 需核实或实现执行端对稳定意图的去重支持。服务端锁、浏览器锁或消息队列本身都不足以证明外部提交恰好一次。
6. 明确重新制作是新的用户意图，并保留与旧尝试的关系；不得把旧状态不明的尝试自动当作失败后重试。

### 验收要求

- 两个会话并发启动相同制作意图，只有一个任务领取者；执行端提交与回执一致。
- 覆盖重复点击、刷新、断线、响应丢失、回执保存失败、租约到期和服务重启。
- 故障注入后仍保留原执行关系，未知请求不自动再次 POST。
- 模拟测试通过后，继续在真实浏览器与目标 ComfyUI 环境验证，分别记录结论。

## 5. 建立逐图验收与正式交付流程

对应 G-05、G-07，并复用 G-02、G-04、G-08 的事实和版本关系。

| 维度 | 示例状态 | 含义 |
| --- | --- | --- |
| 资料 | 待资料、就绪、冲突 | 能否按当前计划制作 |
| 执行 | 未开始、运行中、成功、失败、状态不明 | 执行端发生了什么 |
| 验收 | 待审核、通过、返工、证据不足 | 当前文件是否满足要求 |
| 交付 | 未交付、草稿导出、正式交付 | 用户取得的文件属于何种范围 |

验收覆盖商品身份、轮廓与材质、接口所属面及顺序、配件、未知面、场景尺度和使用逻辑、文案证据、平台要求及整套一致性。自动检测辅助检查；不能确认的项保留未知并进入人工复核，不能凭模型分数补足证据。

审核绑定具体输出版本/哈希及所依据的事实、计划和市场规则版本。换图不能继承旧图的通过状态；事实变更应重新判定受影响项。商品结构、接口或配件关键错误必须返工，不能被审美评分或其他通过项抵消。

草稿允许明确标记后导出。正式交付接口必须在服务端校验选定版本的验收资格，不能只根据执行成功放行。交付清单记录项目、SKU、图号、市场、语言、版本、文件哈希、审核依据、实际源文件、已交付范围和待补项。

输出比例、色彩、格式和体积按项目规格检查。1600 方图、sRGB、JPEG、小于 3MB 是可配置内部起点，不能冒充所有平台的统一规则。仅在确实创建了可编辑源工程时声明提供源文件。

### 验收要求

- 生成成功但接口错面的图片进入返工，无法通过正式交付入口绕过。
- 草稿与正式交付清晰区分，整套完成数只统计当前有效且已验收的文件。
- 导出的独立文件、清单、命名和版本相互一致，缺项明确可见。

## 6. 修复测试假阳性并补全环境证据

对应 D-05，并涉及所有阶段的验证可信度。

- 依各子工程声明和锁文件建立可复现环境，记录 Python、Node、依赖、节点和宿主版本。
- 审计中的架构师 UTF-8 轮为 345 通过、9 个缺依赖错误；这不等于 9 个逻辑缺陷，也不等于全套通过。明确 numpy、cryptography 涉及的功能/测试依赖，保留真实执行结果。
- 统一测试进程文本编码，避免 Windows 编码差异掩盖被测行为。
- 修复 `apps/commerce/tests/contract/test_offline_vision_sample.py`：先验证 CLI 能正常启动，再断言尺寸拒绝的专属错误原因或结构化错误码。
- 缺依赖、启动失败和预期业务拒绝分别报告。不能仅凭退出码 1、未生成目录就让尺寸负例通过，也不能为提高通过率将必需测试静默跳过。
- 分别记录单元/契约测试、真实服务集成、浏览器、ComfyUI Desktop/GPU 和商品图片质量结果。每项审计发现只有在相应层级证据满足后才销项。
