# 映序 Studio 项目闭环 Codex 执行计划书

版本 1.0  |  编制日期 2026年11月19日  |  执行状态 待实施

本计划供项目负责人安排实施、Codex 连续执行和使用者验收使用。首要目标是让一个真实商品的一个 SKU，从资料归档、事实确认、套图策划、逐图制作、对照审核到独立文件交付与案例回流完整运行。沿用已有工程，优先补齐业务关系、执行可靠性和交付资格，随后接通一个明确的 ComfyUI 目标环境并完成真实商品验收。

计划包含 6 个实施阶段、28 个执行任务、30 个必需验收场景，以及全部 15 项已有审计发现的对应关系。任务清单中的 planned 表示尚未实施；本文没有将方案、历史日志或样例演示计为当前项目通过证据。

现状为源码整合基线：电商平台位于 `apps/commerce`，ComfyUI Workflow Architect 2.15.2 位于 `integrations/comfyui-architect`。统一业务层、共享套图项目、正式交付流程和 ComfyUI 业务连接均待开发。既有 15 项审计发现保持待处理。

电商平台现有基础包括 FastAPI、Worker、PostgreSQL、RabbitMQ、私有 S3、React 和图像编辑前端，已有资产版本、任务、报价、租约、回执及原图理解流程。架构师可复用规划、编译、校验和模板；其固定六模块工具保留为一种模板。旧 CI 文件位于子工程目录，新仓库根目录尚无可触发的工作流。当前迁移编号到 0068，后续新增编号需以实施时实际 head 为准。

## 2 第一版范围与业务规则

### 2.1 第一版必须具备的能力

- 选择已有商品或建立商品，管理独立 SKU；一个制作项目只绑定一个 SKU，明确市场、语言、用途和输出规格。
- 归档不可变原图、配件、包装、规格文档、风格和场景参考；记录用途、出处、所属 SKU、物理面、可用角度及版本。
- 复用 AI 理解原图、可编辑描述、人工校订和确认版本；补充未知面、接口归属、配件、尺寸和证据引用。提供明确的人工录入路径。
- 以默认十图、原六模块或自定义图数编排逐图计划；每张图独立处理缺资料、制作、审核、返工和交付。
- 支持人工导入、明确标识的离线样例和真实 ComfyUI 路线，共享同一制作版本、审核和交付模型。
- 对照商品证据审核具体文件版本，按项目规格交付独立文件和清单；允许准确标明范围的部分交付。
- 追踪事实修订影响、历史任务和交付版本；最小案例库保存方案、失败原因与真实反馈。

### 2.2 首版暂缓的范围

桌面外壳、多执行端负载调度、多人协同编辑、公开注册充值、新平台规则全集、视频生产、模型训练、全自动风格推荐、营销投放和自动增长分析暂缓。保留扩展边界，不为这些能力预建微服务或第二套账号系统。当前单用户所有权隔离继续沿用现有 user_id 设计。

### 2.3 不可破坏的产品定义

1. 商品身份、结构、SKU 和证据优先；未知信息保持未知，风格参考不能充当结构证据。
2. 外观锁定遵循 AI 理解原图、用户校订确认、原图与文字共同约束重绘的定义。像素回贴是独立工具，主流程无需划区也能进行。
3. 原图只读保留；事实、策划、工作流和输出分别版本化，历史任务不被后续编辑改写。
4. 默认 01 首图、02 总览、03—08 卖点或场景、09 尺寸、10 包装配件。图序和图数允许按项目调整，稳定图号 ID 与显示顺序分开。
5. 09 需要已确认尺寸；10 同时需要当前 SKU 清单和对应视觉参考。缺项只阻塞受影响图号。
6. 制作成功只表示产生输出。商品关键错误必须返工，审美评分不能抵消；只有当前有效且已验收的独立文件计入成品数。
7. F01—F14 内容随工作渐进记录，已确认数据在适用范围内复用，不变成十四道重复批准。
8. 五风格乘十图用于完整提示词策划的默认展开，不能自动转为五十次真实制作。
9. 1600 方图、sRGB、JPEG、小于 3MB 可作为可配置内部起点。具体平台要求需有对应站点、类目、日期与核验记录。
10. 仅列出真实创建的源文件。工作流 JSON 可以交付为工作流文件，不能声称提供不存在的 PSD 或分层工程。

## 3 工程架构与复用策略

### 3.1 在现有电商工程上建设统一业务层

网页工作台继续使用现有 React 工程；API、业务规则、权限和持久化继续放在 `apps/commerce`。新增 Studio 领域、服务和 API 模块，逐步拆分现有大页面。数据库、消息队列和资产库继续复用现有基础设施。仅在真实差异已经明确时增加抽象，首版不创建独立的新后端和第三套任务系统。

业务链为：工作台操作 → Studio API → 事实与计划版本 → 制作意图 → 既有持久化任务与 Worker → 执行适配器 → 输出资产版本 → 审核 → 交付记录 → 案例。

### 3.2 ComfyUI 作为可连接的执行端

通过薄适配层复用架构师的纯规划、编译和校验能力。统一任务的所有权、领取、状态和回执由业务服务持有；浏览器负责操作和展示。专业用户可以保留原生工作流编辑，但新的制作任务需进入受控协调接口。

默认先支持业务服务与 ComfyUI 同机运行。若采用远程业务服务连接用户本机执行端，必须另行落实可达性、连接代理和访问边界，不能假设远程服务可以访问用户的 127.0.0.1。Desktop 的发现、认证、模型节点和实际执行能力，以目标版本实测为准。

### 3.3 增量变更与兼容原则

原有单图任务、报价快照、账本、回执、登录和资产版本保持原含义。新能力通过新增表、接口与显式关联接入。旧数据进入 Studio 时建立明确 SKU 关系，不能推测补全历史事实。保留来源版本、许可证和导入基线；修改记录独立维护，不把初始来源清单改写成新的运行证明。

任务明细中标注“新增”的路径是建议落点，实施时可按实际结构调整，但要记录原因和最终位置。所有子工程命令都从各自根目录运行。

## 4 数据对象与版本合同

### 4.1 最小对象关系

商品 → SKU → 制作项目 → 图号 → 制作版本 → 审核记录 → 交付文件。事实、素材和计划作为带版本的输入关联到制作版本。交付记录引用具体审核与文件，不指向随时可变的“最新结果”。

| 对象 | 最低记录内容 | 约束 |
| --- | --- | --- |
| SKU | 商品、变体、配件清单、适用范围 | 不因型号相同自动共享事实 |
| 项目 | SKU、工作类型、市场、语言、用途、规格 | 首版一项目一 SKU，不同语言先建关联项目 |
| 事实版本 | 内容、状态、条件、来源、适用 SKU、确认人和时间 | 状态为 confirmed、unknown、conflict；冻结与事实状态分开 |
| 素材版本 | asset_version_id、SHA256、用途、物理面、出处 | 使用确切版本，不仅保存文件名 |
| 图号 | 稳定 slot_id、显示顺序、目标、所需证据和路线 | 排序不能改变历史身份 |
| 计划版本 | 事实和素材引用、文案、角度、规格、工作流关系 | 确认后不可覆盖，只能创建新版本 |
| 执行意图与尝试 | 稳定意图键、请求摘要、执行端、回执、状态 | 同键同请求复用，同键不同摘要拒绝 |
| 输出版本 | 实际文件、输入链、来源路线、技术信息、哈希 | 每次替换新建版本，不继承审核 |
| 审核记录 | 输出哈希、事实和计划版本、问题、判定、审核人 | 针对交付候选字节审核 |
| 交付与案例 | 文件范围、审核依据、清单、待补、案例出处 | 历史可追溯，不伪造源文件和营销结果 |

### 4.2 版本和引用的强约束

所有业务关系带 user_id，并通过实际数据库组合外键、RLS 和角色权限验证所有权；只做前端筛选不满足隔离要求。允许共享适用事实时，应有明确适用范围与来源，不能绕过 SKU 关系。

制作快照至少包含 schema_version、project_id、sku_id、slot_id、plan_revision、fact_revision_ids、asset_version_ids 与哈希、确认描述、execution_profile、workflow_hash 和目标环境快照。模型字节无法核验时记录 unknown，并说明同名模型变化的处理办法。

交付清单至少包含项目与 SKU、市场语言用途、计划版本、已交付图号、文件名、文件哈希、规格、输出版本、审核记录、实际源文件、待补图号及原因、生成时间和交付范围。清单同时提供机器可读 JSON 和用户可读版本。

## 5 状态转换与异常处理

### 5.1 四类状态分别记录

| 维度 | 建议状态 | 关键转换 |
| --- | --- | --- |
| 资料 | missing、ready、conflict | 补证据后按图号重算，冲突不自动消解 |
| 执行 | not_started、queued、submitting、running、succeeded、failed、unknown、cancelled | succeeded 进入待审核，unknown 先对账 |
| 审核 | pending、passed、rework、insufficient_evidence、stale | 新输出或相关依据变化使旧资格不再适用于当前版本 |
| 交付 | none、draft、partial、complete | complete 要求范围内全部图号均有当前有效文件和审核 |

执行尝试进入 submitting 前，必须已保存稳定意图和输入快照。收到回执后保存实际执行编号和原始响应，再更新进度。任务已知编号时可恢复查询；不能确认执行端是否受理时进入 unknown，超时、页面刷新、租约到期或进程重启都不能自动重发。

服务端唯一约束、租约和 fencing token 用于协调所有权；它们无法独自证明外部执行恰好一次。如果目标宿主缺少稳定意图去重能力，采用至多一次提交尝试加未知对账的策略，并诚实保留结果不明的状态。

### 5.2 三个容易遗漏的并发边界

- 更新策划或事实采用 revision 检查，旧页面覆盖新版本时返回明确冲突，不采用最后写入者静默胜出。
- 文件转换在审核前完成，审核绑定交付候选字节。改变尺寸、格式或会改变文件的选项时生成新候选并重新审核，正式打包不临时重编码。
- 交付先准备文件，再在受控事务中核对版本和资格并完成记录。准备中失败或事实发生相关变更，不能留下有效完成记录；已下载的历史包保留原依据并可标为已被新版本取代。

## 6 用户流程与接口边界

### 6.1 四个日常工作区域

资料区管理商品、SKU、参考职责、AI 理解草稿、校订确认与未知项。套图区管理图数、图号、目标、文案、证据、角度和路线，直接显示每张图能否继续及原因。制作审核区展示制作版本、进度、原图与结果对照、阻断问题和返工。交付区选择已通过文件，展示实际完成数、独立文件、清单和待补项，并提供案例回流。

每个区域都应给出当前最有用的下一步。用户不需要理解 fencing token、模型 schema 或队列机制；这些信息放在诊断和专业入口。

## 8 验证分层与证据要求

### 8.1 六层验证不能互相替代

| 层级 | 要证明的内容 | 必要运行环境 |
| --- | --- | --- |
| L1 单元与反例 | 状态、边界、计划、事实和工作流规则 | 锁定依赖与固定样例 |
| L2 API 与协议合同 | 错误原因、输入输出、幂等和版本冲突 | 本地 HTTP 或明确标注的模拟传输 |
| L3 原生服务集成 | 事务、RLS、领取、事件、存储和导出 | 独立 PG、MQ、私有 S3，实际非 owner 角色 |
| L4 真实浏览器 | 用户可完成流程、刷新恢复和并发操作 | 生产构建前端及真实本地服务 |
| L5 真实执行端 | 目标宿主兼容、执行、回收与恢复 | 固定 ComfyUI 或 Desktop 实际版本 |
| L6 真实商品质量 | 商品一致性、逐图和整套可交付 | 当前 SKU 原始证据、实际成品及人工签认 |

离线套件和 CI 中真实付费调用必须为零。测试缺依赖、加载错误、必需用例跳过和未启动服务分别记录，不合并成通过率。历史工程报告仅供定位，不能计入当前提交通过证据。不要求为纯文案或低影响可逆调整堆叠测试；本计划测试集中覆盖业务规则、数据迁移、执行副作用和交付资格。

### 8.2 每份证据的最小字段

机器记录包含 case_id、task_id、commit_sha、started_at、environment_id、verification_level、fixture_manifest_hash、expected、observed、result 和 artifact_refs。result 仅使用 PASS、FAIL、BLOCKED、NOT_RUN；缺环境不能记为 PASS。目标执行记录还包含 intent_id、task_id、prompt_id、实际输入输出哈希和脱敏回执引用。

建议证据位于 `docs/execution/evidence/<提交短号>/<任务编号>/`；大图片和原始日志可放私有产物存储，在仓库保存脱敏索引、哈希和读取说明。任何测试截图、回执或报告都不得包含密钥、登录凭证和私有下载签名。

## 11 Codex 工作方法与运行命令

### 11.1 每个任务的固定执行顺序

1. 读取根级 AGENTS、当前 STATUS、本计划、当前任务依赖和涉及路径下适用约定，核对工作区已有变更。
2. 写清本任务预期行为及必要反例，检查是否可复用现有资产、报价、任务、租约和回执能力。
3. 完成一个可运行的纵向增量，包括需要的数据库、API、页面和合同变更，避免只写接口空壳或页面占位。
4. 运行与变更相称的检查；涉及迁移、权限、并发和交付资格时运行真实服务验证。修复失败后重复相关检查。
5. 保存证据并检查差异，更新根级状态和当前任务结果，保留未解决限制。
6. 在既定范围内继续下一个可执行任务。只有确实依赖缺失资料、环境或未获授权外部动作时保留阻塞，并说明需要的具体条件；不为常规实现选择反复请求确认。

建议每任务或紧密相关的小批任务形成独立提交。不得覆盖用户未提交改动，不自动合并或发布，不用大规模重构冲淡阶段目标。

### 11.2 当前仓库已有检查入口

先进入 `apps/commerce`。以下命令来自当前工程入口，实施时以实际锁文件与可用环境复核；integration 和 all 需要专属服务配置，不会因命令存在自动满足环境条件。

```powershell
$env:PYTHONUTF8 = '1'
uv sync --locked
pnpm --dir apps/web install --frozen-lockfile
uv run python scripts/check.py unit
uv run python scripts/check.py task P4-01 --profile offline
uv run python scripts/check.py task P4-02 --profile offline
pnpm --dir apps/web build
uv run python scripts/check.py integration
uv run python scripts/check.py all --profile offline
```

架构师的当前检查入口从 `integrations/comfyui-architect` 运行；需事先配置对应测试解释器和所需依赖，报告文件名应为本次唯一的新文件。

```powershell
python -B tools/run_checks.py --report release-validation-current.json
```

根级 `scripts/studio.ps1`、Studio 专属测试入口和根级 CI 属于 T00-02 及后续任务的待开发产物，不能在它们存在前按“已实现命令”验收。本计划不执行 `setup_local.py`、任何数据库迁移、服务启动或真实模型任务。

## 12 环境资料与主要风险

### 12.1 实施过程中的外部依赖

| 依赖 | 最晚落实阶段 | 缺失时处理 |
| --- | --- | --- |
| 独立开发测试 PG、MQ、S3 和运行时 | M0 建基线，M2/M3 必需 | 可先读代码和准备反例；真实服务检查保持 BLOCKED |
| 一个真实商品两个 SKU 的原图、差异、尺寸及包装参考 | M0 登记，M5 必需 | 使用显式合成样例继续开发，不能标记真实质量通过 |
| 一个可用 ComfyUI 或 Desktop 目标及模型节点 | M4 必需 | 先完成 M3 和连接代码；目标验收与项目完成保持未通过 |
| 真实图像理解及必要模型调用的配置和当次授权 | M5 外观链必需 | 优先用实际可用且已允许的本地能力；人工入口不冒充 AI 证据 |
| 有权确认的使用者最终质量记录 | M5 必需 | 提供逐图证据与待判定项，保持最终质量待确认 |

这些是实施依赖，不要求在计划制作阶段先行提供全部资料。Codex 应在真正影响任务时集中列出缺项，优先推进可独立完成的部分。

### 12.2 风险与应对

- 外部提交不确定。解决办法是稳定意图、持久回执、一次提交尝试、查询对账和人工处理入口；不以浏览器锁或消息队列宣称端到端恰好一次。
- 迁移破坏旧业务。采用增量关系、独立测试实例、新库与升级双路径、角色验证及备份恢复演练，保留原报价与任务语义。
- 商品关键细节漂移。先确认资料和可用角度；审核按真实证据逐项检查。关键结构反复失败时换合成、局部修复或人工路线，不靠连续重试凑合格。
- 包装清单有文字无外观。第 10 图继续待资料，不能根据配件名称想象视觉；其他合格图照常推进。
- 页面完整但链路空心。每阶段交付可运行纵向增量，以真实浏览器和服务记录证明；生产前端构建不可被开发页面截图替代。
- 范围持续扩张。新增请求先判断是否影响本轮闭环；不影响的内容进入后续清单，已明确的核心缺陷和真实验收不得随意后移。

### 13.2 最终核对清单

- 28 个任务均有结果，所有必需任务达到对应验证层级，待环境或待资料没有被当作完成。
- 30 个验收场景均有当前版本证据；所有 FAIL、BLOCKED 和 NOT_RUN 均解决或明确导致项目未验收。
- D-01—D-05 与 G-01—G-10 的原发现保留，每项销项有修复提交、证据和适用范围。
- 至少一个真实 SKU 完成十张独立图的制作审核交付，另一个 SKU 的差异和隔离得到验证。
- 原图理解、校订确认和无划区重绘有真实链路证据；十张图可以按各自条件选择不同制作路线。
- 部分交付、补齐、事实变更、换图失效、未知提交和恢复均能正确表达。
